# Architecture

    Browser ──► Vercel static files (public/)          pages, JS, CSS, questionnaire JSON
       │
       └──────► Vercel functions (api/*.js, Node)  ──► Postgres on Railway
                 validate ► store ► aggregate

There is no build step and no framework. The pages are plain HTML with ES modules.

| URL | File | Purpose |

## API

| Method and path | What it does |
| --- | --- |
| `POST /api/calculator` | Stores one calculator submission |
| `POST /api/survey` | Stores one survey submission |
| `GET /api/results` | Totals. Hidden until `MIN_PUBLIC_N` respondents. Never returns free text |
| `DELETE /api/respondent?id=` | Deletes everything stored under one respondent id |
| `GET /api/admin/responses` | Everything, linked. Needs `Authorization: Bearer <ADMIN_TOKEN>` |
| `GET /api/health` | Database check |

Every write requires `consent: true`. Input is reduced to known ids and bounded values in
`lib/validate.js`; free text is cut to 300 characters.

## Database

Three tables (`lib/schema.js`), created automatically:

- `respondents`: `id` (random UUID from the browser), `created_day`, `lang`
- `calculator_responses`: `respondent_id`, `created_day`, `record_weight` (slider, 0–100), `answers` (JSON)
- `survey_responses`: `respondent_id`, `created_day`, `answers` (JSON), `background` (JSON)

**How the two questionnaires stay connected.** When a person first agrees to save, the browser
creates a random id and keeps it in local storage. Both questionnaires send that id, so their rows
share a `respondent_id`. A person who clears their browser data gets a new id.

**Repeat visits.** Every submission is kept. Totals use only the latest submission per respondent.

**Not stored.** Name, e-mail, IP address, cookie, time of day. The functions write no request log;
Vercel and Railway keep their own platform logs, which this project does not control.

`db/views.sql` adds flat views (`calculator_answers`, `survey_answers`, `linked_answers`) for analysis.

## Scoring

Your answer becomes a number `u` from −1 to +1. A party's stated position is `s` (+1 or −1).
Where a vote or government step is documented, the party also has an acted position `a`
(+1, −1, or 0 for a pledge given up in coalition talks). With the slider at weight `w` (0 to 1):

    position = (1 − w)·s + w·a        (just s where nothing is documented)
    match on the statement = 1 − |u − position| / 2

Important statements count twice. Five half-match statements are added for every party, so a
party with few known positions cannot reach the top on that alone. See `score()` in `public/js/calculator.js`.

## Party data

`public/data/parties.json` is generated by `scripts/build_parties.py` from a private archive plus
hand-entered records. Each position carries its basis; each acted entry carries a note and a source.
